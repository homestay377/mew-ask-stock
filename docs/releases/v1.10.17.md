# mew 问股 v1.10.17

## 采纳外部审计：先修 P1 六条，再做结构重构

收到一份对 v1.10.12 的代码审计。我逐条核实后确认 **11 条属实**，全部按建议修了。下面是核实结果与改动。

## 一、P1 真 bug（六条，都确认过代码位置）

### 1. `_grantedTools` 跨 agent 泄漏 —— 这是越权

`discuss()` 复用同一个 runner 顺序跑多个 agent，原来共用一个 `Set`：

```dart
final Set<String> _grantedTools = <String>{};
```

后果：一个申请了 `workspace_write_file` 的 agent 获批之后，**紧随其后那个本该只读的 agent 也拿到了写权限**。

改法：按 agent id 分桶 + 只读双保险。

```dart
final Map<String, Set<String>> _grantedByAgent = <String, Set<String>>{};
Set<String> _grantedFor(SubAgent agent) => _grantedByAgent.putIfAbsent(agent.id, () => <String>{});
// 双保险：只读 agent 即便有获批记录也拿不到写工具
if (t != null && !(agent.readOnly && readOnlyBlockedTools.contains(name))) { ... }
```

### 2. `Future.timeout` 不取消底层任务

超时只是让 `await` 提前返回并写一个 error，**底层团队照跑、token 照烧**。

```dart
.timeout(limit, onTimeout: () {
  callCtx.cancel.cancel();
  throw TimeoutException('工具执行超时（${limit.inMinutes} 分钟），已取消', limit);
});
```

### 3. `rounds` 只夹了回显

```dart
// 原来：先跑后夹
final rounds = args['rounds'] is int ? args['rounds'] as int : 2;
// 现在：先夹再跑
final rounds = (...).clamp(1, 5);
```

模型传 50 就真跑 50 轮 × 4 个 agent。

### 4. `add_team_tasks` 自动编号撞 id

板上是 `t1, t5, t3` 时，两条追加都拿到 `t5`。改用 `taken` 集合 + `while` 跳过。

### 5. 取消被报成「完成」

`publish` 不看 `_cancel`，界面显示 done 而 `result.cancelled == true`；`runTeamBoard` 取消时把 `running`/`pending` 原地留着，板永远收不了尾。

改：`cancelled` 分支 + 两条路径都收尾（`running → failed('已取消')`、`pending → skipped('已取消')`）+ `close()`。

### 6. 三分步骤污染兜底统计

`_fallbackDigest` 把 reasoning/text 也算成工具调用，会写出「5 次工具调用，涉及：思考、正文、stock_quote」。改为先过滤 `type == tool`。

## 二、结构重构（审计第 1 步）

### 双真相源合并成一条

原来有两份数据：`meta['board']`（JSON 快照）和 `activeTeamBoard`（全局变量）。现在只有一条：

```dart
class TeamBoard extends ChangeNotifier {
  int revision = 0;
  void bump() { revision++; notifyListeners(); }
  void close() { closed = true; bump(); }
}
```

### 用 `run_id` 取代「取最后一个」

`activeTeamBoard` 的实现是 `for (final b in _boards.values) { last = b; }`。Dart 的 `Map` 是 `LinkedHashMap`，**给已存在的 key 重新赋值不改变插入顺序**——于是：

- 会话 A 建板 → `{A}`
- 会话 B 建板 → `{A, B}`
- 会话 A 再次分派 → `{A(新), B}`，顺序不变
- `activeTeamBoard` 返回 **B 的板** → A 的卡片显示 B 的任务，点「终止」会停掉别人会话的子任务

现在有 `boardRegistry`（`run_id → TeamBoard`，本身也是 `ChangeNotifier`），界面靠 `meta['run_id']` 精确定位。

### `meta` 只存 `run_id`

不再把整张板的 JSON 塞进 `meta`。原来会话每 3 秒整份落库，一次长任务能把这行撑到几 MB；现在 `meta` 只有几十字节。

### 删掉两处 400ms 轮询

| 位置 | 原来的问题 |
|---|---|
| `tool_card` | `_liveTeam` 只在 `initState`/`didUpdateWidget` 求值，而 `ToolPart` 是原地改写、不产生新 widget ⇒ **Timer 永不 cancel**，2.5 次/秒 `setState` 直到页面销毁 |
| `sub_agent_sheet` | `_busy` 写了却没用它开关定时器，空闲时也全量重建整个 sheet |

现在都改成 `ListenableBuilder(listenable: boardRegistry)`：有变化才重画，空闲完全不动，后台也不刷。

### 数据源优先级修正

原来 `meta` 读在最前，而 `meta` 是中途快照 ⇒ **分派结束后卡片永远显示「运行中」**。

现在：`output（终态，权威）→ 活板（run_id）→ meta（兜底）`。

### 板回收

`closed` 原来是死字段（全仓库没处置 true）。现在收尾时 `close()`，并在 2 分钟后从注册表摘掉，避免 `SubAgentResult` 全文常驻内存。

## 三、我不同意的表述

审计说 v1.10.12 的修复是「没有消灭错误的数据通路，而是加了一个旁路」。

**结果上对，因果讲反了**。`meta.board` 那条通路本身是设计正确的——`pushBoard` 由 `runTeamBoard` 主动推。塌方点在**消费者收不到通知**（`onUpdate` 没把 `meta` 的变化传到 UI），我当时加了拉取路径而不是修推送链，所以才有两条路。

审计建议的方案（`ChangeNotifier` + `run_id`）方向对，但不是「合并」，而是**把推送真正打通**——打通之后 `activeTeamBoard` 自然可以删掉。
